# 研究開発タスクの計画と検証

このスキルはローカル GUI から指定されたときに使う。GUI はタスクごとに計画画面（01）と検証結果画面（02）を持つ。タスクは何段階でも子を持てる。01 でユーザーと要件を固め、ユーザーが「実装に進む」を確認したら実装と最初の検証を続けて行う。02 のチャットでは、結果について相談し、必要ならコードを直して再検証する。子を持つタスクでは、全子タスクの完了後に 02 で結果を総括する。タスクの完了はユーザーが決める。

現在のタスクの保存先は `tasks/<id>/`。01 の計画は `plan.html` に保存する。実装後および 02 の新しい検証結果は、その実行分だけを `report-draft.html` に書く。GUI が成功した実行の原稿を `reports/0001.html`、`reports/0002.html` のように順番に保存し、過去のレポートは残す。`plan.html` が無く `plan.md` がある既存タスクでは、計画を `plan.md` の Markdown のまま更新する。既存の `reports/*.md` と `result.md` は過去のレポートとして扱い、変換しない。検証用スクリプトは `validation/`、画像・動画・測定データは `evidence/` に置く。画像を作った場合は自分で体裁を確認し、内容の解釈を今回のレポートに書く。JSON 応答は画面表示と状態判定に使い、計画やレポートの本文は含めない。

## HTML 文書の書き方

- `<body>` の中身だけの HTML 断片で書く（完全な文書でもよい）。GUI はスクリプトを無効にした枠で表示し、基本の文字・表・枠のスタイルを差し込む。
- `<script>`、`onclick` などのイベント属性、外部の CSS・フォント・画像・`<iframe>` は使わない。ファイル単体で表示できる形にする。必要な装飾は `style` 属性か文書内の `<style>` に書く。
- 文字ばかりの文書を避ける。構成図・処理の流れ・比較表・結果グラフを、インライン `<svg>` と `<table>` で示す。本文は短く要点を書く。文字で説明すること自体は問題ない。
- SVG には `viewBox` と表示幅の `width`（例: `width="480"`）を付ける。枠より広い場合は GUI が縮める。表示は暗い背景（本文色 `#d9e5da`、背景 `#1b211c`）なので、文字と線は `currentColor` か明示した色を使う。強調色の目安は緑 `#8ccb90`、橙 `#e0ad61`、灰 `#7c8f7e`。一つの文書に複数の SVG を置く場合、`id` を重複させない。
- 強調枠は `<div class="callout note">`（目的・結論）と `<div class="callout important">`（確認したいこと）を使う。
- 画像は `<img src="../evidence/<filename>" alt="説明">`、動画は `<video controls src="../evidence/<filename>"></video>` で参照する。パスは保存後の `reports/` から見た相対パスで、計画（タスク直下）では `evidence/<filename>` でもよい。GUI がこれらを証拠資料 API の URL に置き換えて表示する。
- 専門用語や独自用語を説明してから使い、数式中の記号も定義する。数式は LaTeX 記法で文中は `$...$`、独立した式は `$$...$$` とする（GUI が表示時に変換する。SVG・`<code>`・`<pre>` の中は変換しない）。多数の画像がある場合は、依頼に関係するものを選んで確認し、全画像を一度に Agent の入力へ読み込まない。

- 01 のチャットでは [計画の指示](references/01-plan.md)と[計画のひな型](assets/plan-template.html)を使う。
- 「実装に進む」では保存済み計画に従ってコードを変更し、[検証の指示](references/02-validation.md)と[検証結果のひな型](assets/result-template.html)に従って最初の検証まで行う。
- 02 のチャットでは[検証の指示](references/02-validation.md)と[検証結果のひな型](assets/result-template.html)を使う。依頼に応じて追加検証、コード修正、再検証を行い、新しい結果が得られた場合だけレポートを追加する。
- 作業が独立して検証できる複数の範囲に広がる場合は、JSON の `child_task_proposals` で子タスク案を返す。ユーザーの承認前に子タスクやブランチを作らない。

【共通指示】
- 01 のチャットでは、指定されたタスクの `tasks/<id>/` 内だけを書き換え、開発コードを変更しない。
- 02 のチャットでは、ユーザーの依頼に必要な場合だけ開発コードを変更し、変更後は必ず検証して結果を記録する。ほかのタスクは変更しない。
- 計画外の実装範囲が見つかったら、その場で実装を広げず、理由と子タスク案を返す。親の総括ではコードを変更せず、子の計画・レポート・commitを根拠に達成点と残課題を書く。
- 02 では選択式の質問を作らない。結果がまだ得られない場合は、その理由と必要な情報をチャットで短く伝え、レポートを増やさない。
- `app/` と `.codex/` は変更しない。`task.json` と `chat_*.json` は GUI が管理するので変更しない。
- 通常の計画・実装・検証・総括では Git のコミットとマージを行わない。「タスクを完了」から明示的にコミット・統合担当として呼ばれた場合だけ、指定された作業ブランチの変更をコミットし、指定された統合先へマージして作業ブランチを削除する。競合を確実に解決できない場合はマージを中止する。
- 処理をバックグラウンドで起動した場合、起動時に返された子プロセスまたはセッションだけを待機対象にする。自分自身、現在の Agent 実行、現在のツール呼び出しの終了を待つ処理を作らない。待機対象を特定できない場合は待機せず、状況を報告する。
- 計画画面で実装を開始しない。ユーザーが別途「実装に進む」を確認してから開始する。
