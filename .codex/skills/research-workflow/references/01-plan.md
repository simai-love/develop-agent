# 01 計画

ユーザーの開発目的を確認し、`assets/plan-template.md` に沿って `tasks/<id>/plan.md` を直接作成・更新する。未確認の推測を確定要件として扱わない。必要な調査用スクリプトは同じタスクの `validation/` に置き、開発コードは変更しない。

変更対象と検証条件を独立して扱える作業が複数あるときは、`child_task_proposals` に子タスク案を返す。各案には短いタイトル、目的、変更範囲、検証方法、分ける理由を書く。ファイル数だけを理由に分割しない。案は提案であり、子タスクの作成はユーザーが画面で承認した後に GUI が行う。提案中の親タスクを実装可能と判定しない。

テンプレートの `[ ]` は記入方法を示す案内であり、成果物には残さない。HTML コメントも削除し、実際のタスクの内容に置き換える。専門用語をなるべく避け、短い文を使う。「目的」は、対象と望む変化が一読で分かる一文にし、実装方法を混ぜない。「現状と困っていること」「仮説」「実装方針」「確かめ方」は、短い箇条書き三つ以下を目安にする。

「確認したいこと」は `> [!IMPORTANT]`、「目的」は `> [!NOTE]` の強調枠に入れる。目的の本文は太字にする。質問の本文も太字にし、各質問の選択肢を同じ行に短く並べる。Markdown の見出し `## 確認したいこと` と `## 目的` は変えない。これらの見出しと本文は Web UI の要点欄にも表示される。

「現状と困っていること」は確認できた事実と困りごとを分ける。「仮説」は原因・予想される変化・確かめ方を区別し、事実として断定しない。「実装方針」は変更する対象と意図を最大三つに絞る。「確かめ方」は変更前後を同じ条件で比べ、目的を達成したと判断する条件も示す。「詳細実装方針」は変更するファイル・関数と入出力、作業順、テストを順番に具体的に書く。未確認の内容は作り話で埋めず、「未確認」と明記する。

質問が必要な場合は、計画の最初の節を「確認したいこと」とし、一文で答えられる質問を記す。質問が不要になったら、この節は削除する。計画の末尾に質問を重ねて置かない。質問と選択肢は、ユーザーが迷わず回答できる短い表現にする。

対象・変更範囲・目的の達成条件・確かめ方に実装判断を左右する曖昧さがあれば、`implementation_ready` を `false` とし、具体的な選択肢を持つ質問を返す。質問数は固定せず、判断に必要な質問を返す。各質問には異なる選択肢を2～4個用意する。Web UI は各質問に自由記述欄も表示し、ユーザーは選択肢だけ、自由記述だけ、または両方で答えられる。質問への回答を反映して再判定する。曖昧さが解消し、計画から実装範囲と成否を判断できるときだけ `true` とする。ユーザーによる実装開始操作は別に必要。

出力前に、案内文や HTML コメントが残っていないこと、質問欄と `questions` の質問・選択肢が一致すること、根拠のない数値や確定表現がないことを確認する。

計画チャットの最終出力は `references/plan-response.schema.json` に従う。`message` はユーザー向けの短い説明、`reason` は判定理由。Markdown 本文を JSON に重複させない。`implementation_ready` が `true` の場合 `questions` は空配列にする。分割案がない場合も `child_task_proposals` は必ず空配列で返す。保存した `plan.md` が空なら準備完了としない。
