# 02 検証結果・追加依頼

## 実行と保存

- 「実装に進む」から呼ばれたら、承認済み計画に従ってコードを変更し、「確かめ方」を実行する。結果を今回の `tasks/<id>/report-draft.md` に書く。
- 子タスクの総括を依頼されたら、親の目的と全子のレポート・commitを確認し、達成点、未確認事項、残課題を `report-draft.md` に書く。総括では開発コードを変更しない。
- 02 のチャットから呼ばれたら、追加検証だけなら開発コードを変更しない。修正が必要なら、依頼と計画の範囲でコードを直し、影響を受ける条件を再検証する。新しい結果が得られたら、その実行分だけを `report-draft.md` に書く。
- 計画外の実装範囲が見つかった場合は作業を広げず、`child_task_proposals` に目的、変更範囲、検証方法、理由を記した案を返す。ユーザーの承認前に子タスクやブランチを作らない。
- 過去の `reports/*.md` と既存の `result.md` は編集しない。GUI が原稿を番号付きの新しいレポートに保存する。結果がまだ得られない場合は原稿を書かず、理由と必要な情報をチャットで短く伝える。02 では選択式質問を返さない。

## レポートの書き方

`assets/result-template.md` の見出し順に書き、コメント、`[ ]`、記入方法の説明文は成果物から消す。専門用語をできるだけ避け、各項目は短い箇条書き三つ以下を目安にする。今回の結果だけで読めるようにし、過去の結果との関係が必要ならレポート番号を示す。

- 最初の「結論」は、今回分かったことを一文で端的に書き、`> [!NOTE]` の強調枠で太字にする。仮説を支持しなかった場合や判断できない場合も、そのまま明記する。
- 「定義した確かめ方に対する結果・根拠」では、計画で定めた量や条件ごとに小見出しを作る。同じ条件で比べた変更前後の値、観測資料へのリンク、条件を満たしたかを書く。数値を得られなかった条件は「未確認」とする。画像・動画が説明に必要なら、その条件の下に置いて解釈を添える。
- 「詳細内容」には、今回の実装・追加修正と変更ファイル、検証環境、再現手順、未確認事項と残課題を整理する。コード変更がなければ「コード変更なし」と書く。結果と推測を混ぜず、タスクの完了判断はユーザーに委ねる。

## 検証資料

検証用の関数やスクリプトは `tasks/<id>/validation/`、生成した画像・動画・測定データは `tasks/<id>/evidence/` に保存する。証拠ファイル名には英数字・`.`・`_`・`-` を使い、画像は PNG/JPEG/WebP/GIF、動画は MP4/WebM/MOV、データは CSV/JSON/PDF にする。画像を**自分で生成したら自分で開き**、欠け・崩れ・文字の読みやすさを確認する。その図が何を示すか、判断にどう関係するかを今回のレポートに書く。開いて確認できなかった画像や動画は、その旨を明記する。GUI が原稿を `reports/` に移すため、本文中の資料リンクは `../evidence/<filename>` と書く。JSON の `evidence_files` はタスク直下からの `evidence/<filename>` を使う。

## JSON 応答

最終出力は `references/validation-response.schema.json` に従う。`outcome` は仮説を支持した場合 `supported`、支持しなかった場合 `not_supported`、判断できない場合 `inconclusive`。`evidence_files` には実在する `evidence/` 内の相対パスだけを入れる。結果本文は JSON に重複させず、レポート原稿に残す。結果がなく原稿を書かない場合は `outcome: inconclusive`、`needs_followup: true` とする。

コードを変更した場合は `commit_message` に、その変更を表す簡潔な日本語の文を入れる。総括やコード変更のない検証では空文字列を返す。分割案がない場合も `child_task_proposals` は空配列を返す。コミット操作そのものは GUI がユーザーの完了操作後に行う。
