# プロジェクト・タスク階層と Git 連携の実装提案

## 目的と合意済み要件

現在の「開発項目」を、`プロジェクト → タスク → 子タスク → …` に整理する。階層の深さは制限しない。プロジェクトは実装単位ではなく、配下の仕事と最終承認を束ねる単位とする。

- プロジェクト作成時にプロジェクト名とブランチ名を入力し、`dev` からプロジェクトブランチを作る。同時に最初のタスクを一つ作る。
- 子を持たないタスクは専用ブランチを作らない。02 の検証後、ユーザーの完了操作で所属先のブランチにコミットする。
- タスクの最初の子を作るとき、そのタスク専用のブランチを所属先のブランチから作る。二件目以降の子でもブランチは増やさない。
- 子タスクの作業は親タスクのブランチにコミットする。子を持つタスクは、全子タスクの完了後に 02 で Agent の総括レポートを得て、ユーザーの完了操作で一段上のブランチへ `--no-ff` でマージする。
- 全タスクの完了後、ユーザーがプロジェクトを承認すると、プロジェクトブランチを `dev` へ `--no-ff` でマージする。成功後にブランチを削除する。
- 調査や実装の範囲が広がる見込みがあれば、Agent が子タスクへの分割を提案できる。ユーザーが画面で承認した案だけを GUI が作成する。
- 既存の最上位開発項目は、各項目を包むプロジェクトを作って移行する。旧項目の計画・レポート・子孫と ID は保持する。

今回は設計文書だけを作る。以下に挙げるコード・指示書・README の変更は実装時の対象である。

## 階層とブランチの対応

```text
dev
└─ project/analysis-4f2a9c  ← プロジェクト作成時
   ├─ タスク A（子なし）       ← 完了時に project/... へコミット
   └─ task/82b54e63a1c0      ← タスク B の初回子タスク作成時
      ├─ 子タスク B-1          ← 完了時に task/... へコミット
      └─ task/7ed3f0c928b1   ← B-2 に子ができた場合
         └─ 孫タスク           ← 完了時に task/7ed... へコミット
```

ブランチを持つタスク B-2 の完了では `task/7ed...` を `task/82b...` にマージする。次に B の総括と承認を終え、`task/82b...` を `project/...` にマージする。ブランチを持たない子タスクは、直近の祖先が持つブランチを作業先とする。

プロジェクト名・タスク名は日本語を許可する。入力するブランチ名は英単語に限定せず、安定した Git 名にするため小文字の ASCII 英数字とハイフンからなる slug（例: `flow-validation`）に限定する。実際の Git 名は `project/<slug>-<短いID>` とし、表示名を変更しても改名しない。タスクブランチは `task/<タスクID>` とする。重複、予約名、不正な ref は作成前に検証する。

## 画面上の流れ

1. 「プロジェクトを作成」で名前とブランチ名を入力する。最初のタスク名はプロジェクト名を初期値として編集可能にし、作成結果を確認してから最初のタスクの 01 を開く。
2. 01 の計画チャットに分割案があるときは、理由、各子タスクの目的・範囲・検証条件をカードで表示する。ユーザーは案を編集し、個別または一括で承認できる。却下もできる。単なる提案ではタスクもブランチも作らない。
3. 最初の子の承認時に親タスクのブランチを作り、子タスクを保存する。手動の「子タスクを追加」も同じ処理を通る。親タスクに未コミットの実装変更がある場合は、先にその扱いを決める画面を出し、黙って新ブランチへ持ち越さない。
4. 子のないタスクでは、従来どおり 01 → 実装 → 02 と進む。02 に最新の検証レポートと対象の差分・コミット予定ファイルを表示する。完了ボタンでユーザーが承認すると、Agent が日本語のコミットメッセージ案を作り、GUI の Git 処理が対象ファイルだけをコミットする。
5. 子を持つタスクの 02 には「子タスクの結果を総括」を用意する。全ての子が完了してから Agent が各計画・最新レポート・コミットを読み、達成点、未確認事項、残課題をその親の新しいレポートとして保存する。ユーザーがその総括を確認して「タスクを完了」を押すと、一段上へマージする。
6. プロジェクト画面にはタスクの進捗、最終的な変更一覧、未確認事項、`dev` との差分を表示する。全タスクの完了後にユーザーが「プロジェクトを承認して dev へマージ」を押す。競合時は状態を完了にせず、解消後に再試行できるようにする。

親タスクに子がある場合は、従来の「実装に進む」を直接表示しない。親の 01 は全体計画、02 は子の結果をまとめる画面として扱う。これにより「親自身の実装成功」がないと完了できない現行条件を、総括レポートと全子タスク完了の条件へ置き換えられる。

## 分割提案の判断基準と承認

Agent は、独立して検証できる作業が複数あり、変更対象や成功条件を分けたほうが判断しやすいときに提案する。単に変更ファイルが複数あるだけでは分割しない。01 で計画を整理するときに提案するのが基本で、02 の検証中に新たな実装範囲が見つかった場合も提案してよい。その場合は既存計画の外側にある変更を勝手に実装せず、観測結果を報告して承認を待つ。

提案はチャット本文の文章から推測せず、01 と 02 の JSON Schema に `child_task_proposals` を追加して構造化する。各案は `title`、`purpose`、`scope`、`verification`、`reason` を持つ。GUI が提案 ID、対象の親 ID、計画のハッシュ、承認状態を記録し、承認 API が重複実行と古い案を拒否する。承認時には入力を再検証し、GUI が子の `plan.md` に承認済みの範囲を初期案として保存する。各子の 01 で要件を改めて確認し、Agent の実装可否判定なしに実装を始めない。

提案の採否はユーザーが決める。Agent にタスク作成 API や Git ブランチ作成を直接許さない。ユーザーが修正・却下した案は履歴に残し、同じ案を毎回繰り返し表示しない。提案を承認しても、既存タスクの完了は自動判定しない。

## Git 操作と失敗時の扱い

Git は GUI 側の専用サービスから実行し、Agent はコミットメッセージ案と根拠を返す。ボタン押下後に実際のコミット・マージまで進むため、利用者からは「Agent がコミットする」操作となる。コミット対象とブランチは Agent の自由なコマンドではなく、タスクの記録と Git の差分から GUI が確定する。`git add .` は使わず、選択した変更だけをステージする。`tasks/`、`.venv/`、Agent の一時ファイルは対象外にする。

同じブランチを使う子タスクの変更が混ざらないよう、コード変更の開始時に該当 worktree が clean であることを確認し、同一ブランチへの書き込みを直列化する。ブランチごとに Git worktree を用意し、Agent の実装・検証はその worktree で実行する。現行の `app/agent.py` は常にリポジトリ直下を作業場所にしているため、ここは変更が必要である。`tasks/` の記録は従来の無視対象の保存先を使い、worktree ごとに複製しない。

作成・完了・マージ処理はサーバー側で順序立てる。Git 操作に失敗した場合、タスク状態を完了にせず、途中で作った不要なブランチや worktree は安全に戻す。コミットやマージが成功してからメタデータ更新が失敗した場合に備え、操作 ID と生成した commit hash を記録し、再押下で重複コミットしない。起動時には Git の実状態と記録を照合して復旧を案内する。競合は自動解決しない。`dev` に未取り込みの変更がある場合はプロジェクトの最終マージ前に確認し、必要な統合と再検証を行う。

削除は記録だけでなくブランチにも影響する。未マージのコミットを持つタスク・プロジェクトでは、通常の削除 API による即時削除を禁止し、対象ブランチとコミットを明示する別の確認手順を設ける。既にマージされた履歴は削除しない。

## 保存形式と API の変更案

- `projects/<id>/project.json` に名前、slug、ブランチ、基点 commit、状態、初回タスク ID、マージ commit を保存する。既存の `tasks/<id>/` は維持し、`task.json` に `project_id`、`parent_id`、所有ブランチ、子の有無に応じたブランチ、完了 commit または merge commit を追加する。`projects/` も研究記録なので Git 管理から除外する。
- タスク一覧 API はプロジェクトを独立した最上位レコードとして返す。既存の `parent_id` はタスク間の再帰的関係に使う。表示用の進捗は保存値だけに依存せず、子孫の状態から計算する。
- `POST /api/projects` はプロジェクト・ブランチ・初回タスクをまとめて作る。提案の承認 API と手動作成 API は同じ子タスク作成処理を使う。タスク完了 API は葉のコミットと親のマージを区別し、プロジェクトの最終承認 API は `dev` へのマージを実施する。
- 02 の「総括」は通常の検証実行と区別する専用の Agent 実行種別とレポート種別にする。通常の検証でコード変更がない場合でも総括レポートを保存できるようにする。総括には全子孫の完了 commit と対象ブランチの HEAD を記録し、いずれかが変われば古い総括として完了を止める。完了条件は葉・親・プロジェクトで別々に定義する。
- Git コマンドは `app/git/` などの専用モジュールへ集約し、ブランチ名検証、worktree、差分、コミット、マージ、復旧を分ける。タスク保存や UI のコードから直接 Git コマンドを組み立てない。

## 既存データの移行

既存の各最上位タスクに対し、新しいプロジェクトレコードを作り、元のタスクをその最初のタスクとして紐づける。元のタスク ID・保存フォルダ・レポート・子孫は変えない。プロジェクト名は旧最上位タスク名を初期値とし、ブランチ slug はユーザーが移行画面で指定できるようにする。

旧タスクの過去のコード変更を新規ブランチへ自動で移し替えない。移行時に作るプロジェクトブランチは、clean な `dev` の現在 commit を基点とする。既に完了した旧タスクは「移行前に完了した記録」として表示し、新たなコミットやマージを要求しない。未完了タスクは現在の Git 差分を確認してから作業先を割り当てる。作業ツリーに未コミット変更がある場合は移行を止め、ユーザーに整理を促す。移行はバックアップを取り、再実行してもプロジェクトを二重作成しない。

## 指示書・README の更新対象

実装時には次を同じ仕様に合わせて更新する。

| ファイル | 追加・変更する内容 |
| --- | --- |
| `AGENTS.md` | プロジェクトとタスクの役割、対象 worktree、ボタンによる Git 操作と承認境界、`projects/` と `tasks/` の管理方針 |
| `.codex/README.md` | 01 の分割提案、02 の総括、GUI のコミット・マージ担当範囲 |
| `.codex/skills/research-workflow/SKILL.md` | 親子階層の読み方、Agent が提案だけを行うこと、承認前の子作成禁止、対象外実装の停止、Git 操作を GUI に任せること |
| `references/01-plan.md` と計画用 Schema | 分割の判断基準、各案の必須項目、準備完了判定と分割提案の関係 |
| `references/02-validation.md` と検証用 Schema | 追加範囲の発見時の提案、親の総括レポートの根拠と未確認事項、総括実行の出力形式 |
| `assets/plan-template.md` と `assets/result-template.md` | 親の計画と総括に必要な欄。葉の既存形式は読みやすさを保つ |
| `README.md`、`app/README.md`、`app/static/README.md`、`docs/architecture.md` | 利用者の操作手順、UI と API、保存形式、Git の失敗時の扱い、移行手順 |
| 新設する `app/git/README.md`、`projects/README.md` 相当 | Git モジュールの責務と、無視対象のプロジェクト保存領域の説明 |

`projects/` は Git 管理から除外するため、実行時の各プロジェクトフォルダに README を生成する必要はない。Git 管理する新設フォルダには README を置き、ルート README からリンクする。

## 実装順と確認項目

1. 保存形式、既存データ移行、プロジェクト作成画面を実装する。旧タスクの ID とレポートが残ることを確認する。
2. Git サービスと worktree を実装する。プロジェクト作成、初回子作成、葉のコミット、親の再帰的マージ、最終 `dev` マージを一時リポジトリで確認する。
3. 01 の構造化された分割提案、編集・承認・却下、重複防止を実装する。承認前には子もブランチもできないことを確認する。
4. 02 の親総括と完了条件、プロジェクト最終承認を実装する。未完了の子、古い総括、競合、未コミット変更では完了状態にならないことを確認する。
5. 指示書・README・詳細設計を更新し、既存のチャットと検証が継続して動くことを確認する。Python のデバッグ前には `uv` で同期した `.venv` を有効化する。

本提案の受け入れ条件は、ユーザーが承認した操作だけでタスク作成・コミット・マージが進み、各段階のブランチと Git 履歴からどのタスクの結果かを追えることである。
