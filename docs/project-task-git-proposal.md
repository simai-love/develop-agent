# プロジェクト・タスク階層と Git 連携の実装提案

## 目的と合意済み要件

現在の「開発項目」を、`プロジェクト → タスク → 子タスク → …` に整理する。階層の深さは制限しない。プロジェクトは実装単位ではなく、配下の仕事と最終承認を束ねる単位とする。

- プロジェクト作成時にプロジェクト名とブランチ名を入力し、`dev` からプロジェクトブランチを作る。同時に最初のタスクを一つ作る。
- 子を持たないタスクは専用ブランチを作らない。02 の検証後、ユーザーの完了操作で所属先のブランチにコミットする。
- タスクの最初の子を作るとき、そのタスク専用のブランチを所属先のブランチから作る。二件目以降の子でもブランチは増やさない。
- 子タスクの作業は親タスクのブランチにコミットする。子を持つタスクは、全子タスクの完了後に 02 で Agent の総括レポートを得て、ユーザーの完了操作で一段上のブランチへ `--no-ff` でマージする。
- 全タスクの完了後、ユーザーがプロジェクトを承認すると、プロジェクトブランチを `dev` へ `--no-ff` でマージする。成功後にブランチを削除する。
- 調査や実装の範囲が広がる見込みがあれば、Agent が子タスクへの分割を提案できる。ユーザーが画面で承認した案だけを GUI が作成する。
- 既存の最上位開発項目は、各項目を包むプロジェクトを作って移行する。旧項目の計画・レポート・子孫と ID は保持する。

今回は設計文書だけを作る。以下に挙げるコード・指示書・README の変更は実装時の対象である。

## 階層とブランチの対応

```text
dev
└─ project/analysis-4f2a9c  ← プロジェクト作成時
   ├─ タスク A（子なし）       ← 完了時に project/... へコミット
   └─ task/82b54e63a1c0      ← タスク B の初回子タスク作成時
      ├─ 子タスク B-1          ← 完了時に task/... へコミット
      └─ task/7ed3f0c928b1   ← B-2 に子ができた場合
         └─ 孫タスク           ← 完了時に task/7ed... へコミット
```

ブランチを持つタスク B-2 の完了では `task/7ed...` を `task/82b...` にマージする。次に B の総括と承認を終え、`task/82b...` を `project/...` にマージする。ブランチを持たない子タスクは、直近の祖先が持つブランチを作業先とする。

プロジェクト名・タスク名は日本語を許可する。入力するブランチ名は英単語に限定せず、安定した Git 名にするため小文字の ASCII 英数字とハイフンからなる slug（例: `flow-validation`）に限定する。実際の Git 名は `project/<slug>-<短いID>` とし、表示名を変更しても改名しない。タスクブランチは `task/<タスクID>` とする。重複、予約名、不正な ref は作成前に検証する。

## 画面上の流れ

1. 「プロジェクトを作成」で名前とブランチ名を入力する。最初のタスク名はプロジェクト名を初期値として編集可能にし、作成結果を確認してから最初のタスクの 01 を開く。
2. 01 の計画チャットに分割案があるときは、理由、各子タスクの目的・範囲・検証条件をカードで表示する。ユーザーは案を編集し、個別または一括で承認できる。却下もできる。単なる提案ではタスクもブランチも作らない。
3. 最初の子の承認時に親タスクのブランチを作り、子タスクを保存する。手動の「子タスクを追加」も同じ処理を通る。親タスクに未コミットの実装変更がある場合は、先にその扱いを決める画面を出し、黙って新ブランチへ持ち越さない。
4. 子のないタスクでは、従来どおり 01 → 実装 → 02 と進む。02 に最新の検証レポートと対象の差分・コミット予定ファイルを表示する。完了ボタンでユーザーが承認すると、Agent が日本語のコミットメッセージ案を作り、GUI の Git 処理が対象ファイルだけをコミットする。
5. 子を持つタスクの 02 には「子タスクの結果を総括」を用意する。全ての子が完了してから Agent が各計画・最新レポート・コミットを読み、達成点、未確認事項、残課題をその親の新しいレポートとして保存する。ユーザーがその総括を確認して「タスクを完了」を押すと、一段上へマージする。
6. プロジェクト画面にはタスクの進捗、最終的な変更一覧、未確認事項、`dev` との差分を表示する。全タスクの完了後にユーザーが「プロジェクトを承認して dev へマージ」を押す。競合時は状態を完了にせず、解消後に再試行できるようにする。

親タスクに子がある場合は、従来の「実装に進む」を直接表示しない。親の 01 は全体計画、02 は子の結果をまとめる画面として扱う。これにより「親自身の実装成功」がないと完了できない現行条件を、総括レポートと全子タスク完了の条件へ置き換えられる。

02 で実装途中に分割が必要になった場合は、現在の変更を別の子へ黙って移さない。画面はまず「ここまでの範囲を検証して確定」を案内し、ユーザーの完了操作で現在の差分をコミットする。その後、最初の子を承認した時点で元タスクを親へ昇格させ、先のコミットを `pre_split_commit` として残し、状態を再び進行中にする。新しい親ブランチはそのコミットを含む所属先の HEAD から作る。最終総括は昇格前の検証結果と子の結果を合わせて扱う。プロジェクトが既に `dev` へマージ済みなら昇格は許可しない。この状態の変更は画面で明示し、ユーザーが選べるようにする。

## 分割提案の判断基準と承認

Agent は、独立して検証できる作業が複数あり、変更対象や成功条件を分けたほうが判断しやすいときに提案する。単に変更ファイルが複数あるだけでは分割しない。01 で計画を整理するときに提案するのが基本で、02 の検証中に新たな実装範囲が見つかった場合も提案してよい。その場合は既存計画の外側にある変更を勝手に実装せず、観測結果を報告して承認を待つ。

提案はチャット本文の文章から推測せず、01 と 02 の JSON Schema に `child_task_proposals` を追加して構造化する。各案は `title`、`purpose`、`scope`、`verification`、`reason` を持つ。GUI が提案 ID、対象の親 ID、計画のハッシュ、承認状態を記録し、承認 API が重複実行と古い案を拒否する。承認時には入力を再検証し、GUI が子の `plan.md` に承認済みの範囲を初期案として保存する。各子の 01 で要件を改めて確認し、Agent の実装可否判定なしに実装を始めない。

提案の採否はユーザーが決める。Agent にタスク作成 API や Git ブランチ作成を直接許さない。ユーザーが修正・却下した案は履歴に残し、同じ案を毎回繰り返し表示しない。提案を承認しても、既存タスクの完了は自動判定しない。

## Git 操作と失敗時の扱い

Git は GUI 側の専用サービスから実行し、Agent はコミットメッセージ案と根拠を返す。ボタン押下後に実際のコミット・マージまで進むため、利用者からは「Agent がコミットする」操作となる。コミット対象とブランチは Agent の自由なコマンドではなく、タスクの記録と Git の差分から GUI が確定する。`git add .` は使わず、選択した変更だけをステージする。`tasks/`、`.venv/`、Agent の一時ファイルは対象外にする。

同じブランチを使う子タスクの変更が混ざらないよう、最初のコード変更時に該当 worktree が clean であることを確認し、その後は完了まで一つのタスクに変更を予約する。同じタスクによる 02 の修正・再検証は許可する。ブランチごとに Git worktree を用意し、Agent の実装・検証はその worktree で実行する。現行の `app/agent.py` は常にリポジトリ直下を作業場所にしているため、ここは変更が必要である。`tasks/` の記録は従来の無視対象の保存先を使い、worktree ごとに複製しない。

作成・完了・マージ処理はサーバー側で順序立てる。Git 操作に失敗した場合、タスク状態を完了にせず、途中で作った不要なブランチや worktree は安全に戻す。コミットやマージが成功してからメタデータ更新が失敗した場合に備え、操作 ID と生成した commit hash を記録し、再押下で重複コミットしない。起動時には Git の実状態と記録を照合して復旧を案内する。競合は自動解決しない。`dev` に未取り込みの変更がある場合はプロジェクトの最終マージ前に確認し、必要な統合と再検証を行う。

削除は記録だけでなくブランチにも影響する。未マージのコミットを持つタスク・プロジェクトでは、通常の削除 API による即時削除を禁止し、対象ブランチとコミットを明示する別の確認手順を設ける。既にマージされた履歴は削除しない。

## 保存形式と API の変更案

- `projects/<id>/project.json` に名前、slug、ブランチ、基点 commit、状態、初回タスク ID、マージ commit を保存する。既存の `tasks/<id>/` は維持し、`task.json` に `project_id`、`parent_id`、所有ブランチ、子の有無に応じたブランチ、完了 commit または merge commit を追加する。`projects/` も研究記録なので Git 管理から除外する。
- タスク一覧 API はプロジェクトを独立した最上位レコードとして返す。既存の `parent_id` はタスク間の再帰的関係に使う。表示用の進捗は保存値だけに依存せず、子孫の状態から計算する。
- `POST /api/projects` はプロジェクト・ブランチ・初回タスクをまとめて作る。提案の承認 API と手動作成 API は同じ子タスク作成処理を使う。タスク完了 API は葉のコミットと親のマージを区別し、プロジェクトの最終承認 API は `dev` へのマージを実施する。
- 02 の「総括」は通常の検証実行と区別する専用の Agent 実行種別とレポート種別にする。通常の検証でコード変更がない場合でも総括レポートを保存できるようにする。総括には全子孫の完了 commit と対象ブランチの HEAD を記録し、いずれかが変われば古い総括として完了を止める。完了条件は葉・親・プロジェクトで別々に定義する。
- Git コマンドは `app/git/` などの専用モジュールへ集約し、ブランチ名検証、worktree、差分、コミット、マージ、復旧を分ける。タスク保存や UI のコードから直接 Git コマンドを組み立てない。

## `app/` の実装設計

以下の関数名・引数は実装時の目安である。Git 操作と記録の更新を一つの場所で順序づけ、HTTP ハンドラと Agent 実行側から同じ業務処理を呼ぶ構成にする。

### 保存層: `app/project_storage.py` と `app/storage.py`

| 関数 | 入力と戻り値 | 変更方針 |
| --- | --- | --- |
| 新設 `create_project_record(root, name, slug, branch, initial_task_id, base_commit)` | プロジェクト保存先と作成情報 → project dict | Git 側の作成成功後に `project.json` を原子的に保存する。ID と表示名はブランチ名から独立させる。 |
| 新設 `read_project(root, project_id)` / `list_projects(root)` | ID または保存先 → project dict の一件または一覧 | 作成時刻順に返す。進捗は子孫タスクから導出し、保存値として増やさない。 |
| 変更 `create_task(root, title, parent_id, project_id, initial_plan='')` | タスク情報 → task dict | ルートタスクには `parent_id=None` と `project_id` を要求する。子は親と同じプロジェクトに固定する。承認済み分割案の初期計画を保存できるようにする。 |
| 変更 `read_task` / `save_metadata` / `list_tasks` | 従来の入出力を維持 | `project_id`、`branch`、`commit_hash`、`pre_split_commit`、`merge_hash`、`legacy_completed` を読み書きする。古いレコードは移行処理で補い、通常読み込み時に暗黙の書き換えをしない。 |
| 新設 `save_child_proposals(root, task_id, proposals, plan_hash)` | 構造化案 → 保存した提案一覧 | 案 ID と `pending/approved/rejected` を記録する。チャットの `message` に埋め込まず、承認履歴を後から読める形にする。 |
| 新設 `claim_proposal(root, task_id, proposal_id, edited_fields)` | 承認対象 → 確定した案 | 親 ID、計画ハッシュ、状態を検証する。同じ案の再送には前回作成した子 ID を返す。却下は別の状態更新とする。 |
| 分離 `complete_task` → `mark_task_completed(root, task_id, git_hash, kind)` | 完了根拠 → task dict | ストレージ層は Git を実行しない。`kind` は `commit` または `merge`。従来の `result` 一致判定は業務層で最新レポートの番号と内容ハッシュの確認に置き換える。 |
| 変更 `append_report(..., report_kind='validation', summary_basis=None)` | 検証または総括の結果 → task dict | 親総括はコード変更ゼロでも保存する。子孫の commit とブランチ HEAD を `summary_basis` に残す。旧 `result.md` の読み取り互換性を維持する。 |
| 変更 `task_subtree` / `delete_task` | 従来の入出力を維持 | 同一プロジェクト内だけを辿る。Git に未マージの作業がある場合の削除可否は業務層で先に判定する。 |

作成途中の不整合を避けるため、プロジェクト作成と初回タスク作成では確保した ID を先に決め、Git の ref・worktree を作成し、記録を書き込む。途中失敗時は新しく作ったものだけを戻す。操作中であることを操作記録に残し、サーバー再起動後に照合できるようにする。

### Git 層: `app/git/`

`app/git/repository.py` に Git の単一コマンド実行関数 `run_git(repo, args)`、ref 検証 `validate_branch_slug(slug)`、HEAD 取得 `head_commit(repo, branch)`、差分取得 `changed_paths(worktree)` を置く。引数は配列で渡し、シェル文字列を組み立てない。差分はファイル名の改行・空白を扱えるよう `-z` 形式で読み、対象外パスを検証する。

`app/git/worktree.py` に `ensure_worktree(repo, branch, location)` と `remove_worktree(repo, branch)` を置く。worktree は本体の外側にある専用保存先へ配置し、既存 ref とパスの対応を確認してから再利用する。ブランチ削除前に worktree を外す。

`app/git/operations.py` に次の操作を置く。

| 関数 | 入力 → 出力 | 主な前提と手順 |
| --- | --- | --- |
| `create_project_branch(repo, slug, project_id)` | slug と ID → ブランチ名、基点 commit、worktree | `dev` の存在、元 worktree の状態、ref の重複を確認し、現在の `dev` の HEAD から作成する。 |
| `create_task_branch(repo, task_id, source_branch)` | ID と親の作業ブランチ → タスクブランチと worktree | 親側に未コミットの変更がなく、親に別の実行がないことを確認する。親ブランチ HEAD を基点にする。 |
| `commit_task(worktree, paths, message, operation_id)` | 所属 worktree と確定したファイル → commit hash | 予約中のタスクの変更だけをステージし、`git diff --cached` を再確認して日本語メッセージでコミットする。空コミットは作らない。 |
| `merge_task(repo, source, target, operation_id)` | 子・親ブランチ → merge commit hash | 両 worktree の状態と source HEAD を確認し、target 側で `--no-ff` マージする。成功後に source の worktree とブランチを片付ける。 |
| `merge_project(repo, source, operation_id)` | プロジェクトブランチ → `dev` の merge commit hash | 対象差分と `dev` の状態を再確認し、`--no-ff` マージする。成功後にプロジェクト worktree とブランチを片付ける。 |

Git 層はタスクの完了条件を知らない。マージ競合では target に中途半端な状態を残さず `git merge --abort` を試み、失敗内容を業務層へ返す。Git がすでに成功した操作は commit hash を照合して再実行しない。

### 業務層: 新設 `app/workflow.py`

`WorkflowService` に `create_project(name, slug, first_task_title)`、`create_child(parent_id, title, initial_plan, proposal_id=None)`、`complete_leaf(task_id, report_number, message)`、`complete_parent(task_id, summary_report_number)`、`complete_project(project_id)` を置く。各メソッドは入力 ID からプロジェクトと作業ブランチを解決し、Agent 実行・Git 操作・メタデータ変更の排他を管理する。戻り値は更新したレコードと Git hash とする。

- `create_child` は親の状態、同一プロジェクト所属、初回子かどうかを確認する。初回なら `create_task_branch` を実行してから子を保存し、親にブランチを記録する。親が完了済みの葉なら、プロジェクトが未完了であることを確かめ、既存の完了 commit を `pre_split_commit` に残して親へ昇格させる。未コミット変更が残る葉は先に検証・完了させる。承認済み提案なら `claim_proposal` と子作成を一つの操作 ID で結ぶ。
- `complete_leaf` は子がないこと、最新レポート番号と検証状態、予約中のファイル、現在の差分、他タスクの実行がないことを確認する。GUI に表示した対象ファイル・HEAD が古ければ再確認を要求し、コミット後に完了状態と hash を保存する。
- `complete_parent` は全ての直下の子が完了し、総括の `summary_basis` が現在の子孫 commit と HEAD に一致することを確認する。ブランチをマージしてから親を完了にする。孫以下は直下の完了条件を通じて保証する。
- `complete_project` は全ての直下タスクが完了し、表示した `dev` とプロジェクトブランチの HEAD が変わっていないことを確認する。`dev` にマージした後でプロジェクトを完了にする。
- `delete_task` / `delete_project` もここに置き、未マージ Git 履歴、実行中 Agent、子孫への影響を確認してから記録を削除する。

ThreadingHTTPServer から同時に呼ばれるため、現在の `AgentManager.lock` と別に Git 操作を直列化するロックを用意する。ロックの取得順を一つに決め、同じタスクやブランチへの同時操作を拒否する。操作 ID、開始時 HEAD、作成した hash、進行段階は `projects/<id>/operations/` に保存する。復旧処理は起動時に進行中の操作を読み、Git の実状態から完了・再試行・手動確認を判定する。

### Agent 実行: `app/agent.py`

| 現行関数 | 変更方針 |
| --- | --- |
| `AgentManager.__init__` | `WorkflowService` または Git worktree 解決器を受け取る。タスク記録の絶対パスと、コード用 worktree のパスを別々に保持する。 |
| `start_chat` | 01 と通常の 02 に加え、`kind='summary'` を別の入口として用意する。通常 02 の `changed_files` 必須条件を総括には適用しない。 |
| `start_implementation` / `_start` | 子を持つ親では実装を拒否する。対象ブランチの作業権を確保し、初回実装前だけ clean を確認する。実行中・保留中の別タスクが同じブランチに触れられないようにする。 |
| `_work` | 01 は従来どおりタスク保存先を `cwd` / `--cd` とし、その場所への書き込みに限定する。実装・通常の 02 は予約 worktree を `cwd` / `--cd` に使い、レポートは中央の `tasks/` に残す。総括はコードを書かない専用実行にする。 |
| `_chat_prompt` / `_implementation_prompt` | プロジェクト名、祖先の目的、対象ブランチと worktree、許可された変更範囲を明示する。分割提案の条件と承認境界をプロンプトに含める。 |
| `_validate_result` | 追加された分割案の構造を検証する。総括は別の Schema と検証関数で扱い、子タスクのレポートと commit hash を根拠として要求する。 |
| `_change_snapshot` | `project_root` 固定をやめ、worktree を引数に取る。ファイル名を `-z` で取得し、前後の変化とタスクの予約対象を照合する。 |
| `recover_interrupted_runs` | 実行状態の復旧に加え、予約 worktree の未コミット差分を消さず、同じタスクから再検証できる状態にする。 |

01 の Agent は対象タスクの `plan.md` 以外を書き換えない。分割案は Schema の応答を `app/storage.py` が保存する。02 の Agent が見つけた新しい実装範囲は構造化案として返し、ユーザーの承認と子タスクの 01 を経る。親総括ではコード変更を許さない。Agent の通常実行で Git commit/merge を許可する必要はない。

worktree をリポジトリ本体の外に置くと、実装・02 の Agent から中央の `tasks/<id>/report-draft.md` へ書ける設定が必要になる。Codex CLI には対象タスク保存先だけを追加の書き込み許可範囲として渡す方法を実装時に確認する。対応できない CLI では、レポート本文を構造化応答として受けて GUI が保存する方式へ切り替える。中央の `tasks/` 全体や他タスクへの書き込み権限は与えない。

### HTTP と表示: `app/server.py`、`app/task_status.py`、`app/static/`

`Handler.do_GET` に `GET /api/projects` と `GET /api/projects/<id>` を追加し、`GET /api/tasks` は `project_id` 付きタスクを返す。`Handler.do_POST` は URL ごとに小さな処理関数へ分け、`POST /api/projects`、`POST /api/tasks/<id>/children`、`POST /api/tasks/<id>/proposals/<proposal_id>/approve`、`POST /api/tasks/<id>/summary`、`POST /api/tasks/<id>/complete`、`POST /api/projects/<id>/complete` を `WorkflowService` に委譲する。提案却下には `POST .../reject` を設ける。完了 API は最新のレポート番号と画面が確認した HEAD を受け取り、古い画面からの操作を拒否する。サーバーは UI の disabled 状態に頼らず同じ条件を検証する。

`present_task` と `display_status` は、葉なら計画・実装・検証・コミット、親なら子の進捗・総括・マージ待ちを表示する。`present_project` を追加して、プロジェクトの最終承認待ちや競合を表示する。API の失敗は `400` にまとめず、不正入力、古い画面、Git 競合を画面が区別できるコードとメッセージにする。

ブラウザ側は `state.projects` と `state.project` を追加する。`renderTree()` はプロジェクトを最上段に置き、その下へ既存の `parent_id` による再帰表示を接続する。`subtreeIds()` は削除対象の子孫確認に使い続ける。`render()` は選択対象をプロジェクト・葉・親で分け、親に総括ボタン、プロジェクトに最終承認ボタンを表示する。`openCreate()` はプロジェクト作成と子タスク作成のダイアログを分ける。`renderChat()` に分割案カードを追加し、承認・編集・却下のイベントを `bindEvents()` へ追加する。`refreshTasks()` と `selectTask()` はプロジェクト一覧とタスク一覧を更新し、画面更新後も同じ対象を開く。`renderReports()` は通常検証と親総括を区別し、完了前に対象差分・ブランチ・コミットメッセージ案を表示する。

`index.html` にはプロジェクト作成、分割案の承認、親総括、最終マージの画面要素を追加する。`styles.css` は既存のツリーとカードの見た目を使い、階層が深い場合の省略表示と狭い画面での操作性を調整する。`markdown.mjs` の証拠資料リンクは従来のタスク ID を使い続ける。

### 具体的な処理順

| 操作 | 順序 |
| --- | --- |
| プロジェクト作成 | 入力検証 → ID 確保 → `dev` HEAD 記録 → ブランチ・worktree 作成 → プロジェクトと初回タスク保存 → UI 更新 |
| 初回子タスク作成 | 親と差分の確認 → タスクブランチ・worktree 作成 → 親にブランチを記録 → 子タスク保存 → 提案を承認済みにする |
| 葉の完了 | 最新検証と差分を照合 → コミットメッセージ・ファイルをユーザーに表示 → 対象だけステージ・コミット → hash 保存 → 完了表示 |
| 親の完了 | 全子の完了確認 → 総括を生成・表示 → ユーザー承認 → 総括基点を再照合 → `--no-ff` マージ → hash 保存・ブランチ整理 |
| プロジェクト完了 | 全タスクの完了確認 → `dev` との差分表示 → ユーザー承認 → HEAD 再照合 → `--no-ff` マージ → hash 保存・ブランチ整理 |

この順序のうち「検証結果を見た後のユーザー承認」を伴う部分は、画面と API の両方で別の操作として扱う。Agent の終了イベントだけでコミットやマージを始めない。

## 既存データの移行

既存の各最上位タスクに対し、新しいプロジェクトレコードを作り、元のタスクをその最初のタスクとして紐づける。元のタスク ID・保存フォルダ・レポート・子孫は変えない。プロジェクト名は旧最上位タスク名を初期値とし、ブランチ slug はユーザーが移行画面で指定できるようにする。

旧タスクの過去のコード変更を新規ブランチへ自動で移し替えない。移行時に作るプロジェクトブランチは、clean な `dev` の現在 commit を基点とする。既に完了した旧タスクは「移行前に完了した記録」として表示し、新たなコミットやマージを要求しない。未完了タスクは現在の Git 差分を確認してから作業先を割り当てる。作業ツリーに未コミット変更がある場合は移行を止め、ユーザーに整理を促す。移行はバックアップを取り、再実行してもプロジェクトを二重作成しない。

## 実装順と確認項目

1. 保存形式、既存データ移行、プロジェクト作成画面を実装する。旧タスクの ID とレポートが残ることを確認する。
2. Git サービスと worktree を実装する。プロジェクト作成、初回子作成、葉のコミット、親の再帰的マージ、最終 `dev` マージを一時リポジトリで確認する。
3. 01 の構造化された分割提案、編集・承認・却下、重複防止を実装する。承認前には子もブランチもできないことを確認する。
4. 02 の親総括と完了条件、プロジェクト最終承認を実装する。未完了の子、古い総括、競合、未コミット変更では完了状態にならないことを確認する。
5. 指示書・README・詳細設計を更新し、既存のチャットと検証が継続して動くことを確認する。Python のデバッグ前には `uv` で同期した `.venv` を有効化する。

本提案の受け入れ条件は、ユーザーが承認した操作だけでタスク作成・コミット・マージが進み、各段階のブランチと Git 履歴からどのタスクの結果かを追えることである。
